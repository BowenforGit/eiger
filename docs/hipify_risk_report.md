# HIP Portability Risk Report

## What hipify does here
- `tools/build_amd.py` runs `hipify_python` over `src/cuda/**` plus the three CMakeLists in `src/cuda` and writes results in-place unless `--output-directory` is given; it also plugs in `tools/custom_hipify_mapping.json` and only adds a handful of include roots.
- Custom mappings mainly remap cuCollections/CUB symbols to HIP equivalents (hipco/hipcub) and `cuda::stream_ref` to `hipco::experimental::cuda_stream_ref`. Anything outside that list is left to upstream hipify defaults; missing mappings will surface as build failures post-translation.
- Clean mode only deletes generated `hip/` dirs and `*_hip.*` files; it does not roll back other edits.

## High-risk correctness gaps when running on ROCm
- Warp-size baked as 32: the join path assumes 32-lane warps for shared-memory sizing and ballots (e.g., `wid = tid/32`, shared tiles dimensioned with `NT/32`) in [src/cuda/operators/join/partition_hash_join.cu](src/cuda/operators/join/partition_hash_join.cu#L43-L53) and [src/cuda/operators/join/partition_hash_join.cu](src/cuda/operators/join/partition_hash_join.cu#L174-L183), and in merge-path buffers in [src/cuda/operators/join/merge_path.cuh](src/cuda/operators/join/merge_path.cuh#L184-L191). HIP wavefronts are 64-wide, so ballots/shuffles will drop half the lanes or overflow local buffers.
- 32-bit ballot masks with 64-lane wavefronts: joins use `int mask`/`threadmask` with `__ballot_sync(__activemask(), ...)` and `__shfl_sync` assumptions in [src/cuda/operators/join/partition_hash_join.cu](src/cuda/operators/join/partition_hash_join.cu#L262-L335) and [src/cuda/operators/join/merge_path.cuh](src/cuda/operators/join/merge_path.cuh#L200-L256). On ROCm, ballots return 64-bit masks; truncation will corrupt match counting and buffer flushing logic.
- Shared-memory size assumptions tuned for NVIDIA: `partition_hash_join` computes dynamic smem with hard-coded `join_kernel_tb_size=512`, bucket sizes, and `shuffle_space_size` (see [src/cuda/operators/join/partition_hash_join.cu](src/cuda/operators/join/partition_hash_join.cu#L26-L71)), easily exceeding the 64 KB LDS limit on gfx90a. HIP will reject the launch or silently cap smem, leading to spills.
- Device info hard-coded per architecture with no CMake propagation: [src/cuda/utils/device_info.hpp](src/cuda/utils/device_info.hpp) `static_assert(false)` unless a macro like `ROCm_gfx90a` is predefined. No CMake target sets these macros, so a ROCm build will fail to compile unless users pass `-DROCm_gfx90a`, and even then warp/SM counts stay NVIDIA-centric.
- Hash groupby uses CU-only cuCollections features: `cuco::thread_scope_device` and `cuco::storage<1>` are gated under `__NVCC__` in [src/cuda/operators/groupby/groupby_hash.cu](src/cuda/operators/groupby/groupby_hash.cu#L240-L317). HIP builds will drop these arguments; hipco may require different thread scopes/storage or may misbehave if defaults differ.
- Cooperative-groups async copy is CUDA-only: `cooperative_groups::memcpy_async` paths are wrapped in `#ifdef __NVCC__` in [src/cuda/operators/groupby/agg_helper.cuh](src/cuda/operators/groupby/agg_helper.cuh#L1-L120) and the shared-memory flush helpers [src/cuda/operators/groupby/agg_helper.cuh](src/cuda/operators/groupby/agg_helper.cuh#L230-L285). HIP-compiling these kernels will skip the async copy entirely, leaving uninitialized outputs if the code path is enabled later.

## Medium-risk build/compat issues
- Benchmarks CMake links `nvbench::main` even under `USE_ROCM` in [src/cuda/benchmarks/CMakeLists.txt](src/cuda/benchmarks/CMakeLists.txt#L1-L27); hipbench exposes different targets, so ROCm benchmark builds likely fail.
- Tests and library sources compiled on ROCm are a strict subset of CUDA: CMake omits joins, many string ops, and additional kernels under `USE_ROCM` (see [src/cuda/CMakeLists.txt](src/cuda/CMakeLists.txt#L17-L66) and [src/cuda/tests/CMakeLists.txt](src/cuda/tests/CMakeLists.txt#L1-L45)), leaving large functionality unported and untested.
- CUDA occupancy helpers and function attributes rely on CUDA names: `cudaOccupancyMaxPotentialBlockSize`/`cudaFuncSetAttribute` appear throughout (e.g., [src/cuda/utils/launch.cuh](src/cuda/utils/launch.cuh#L1-L21), [src/cuda/operators/groupby/groupby_hash.cu](src/cuda/operators/groupby/groupby_hash.cu#L300-L335), [src/cuda/operators/join/merge_path.cuh](src/cuda/operators/join/merge_path.cuh#L284-L294)). HIP provides analogs, but hipify sometimes needs explicit remaps; failures will surface as missing symbols or ignored smem tuning.
- NVTX usage in benchmarks: NVTX headers/marks remain in benchmark sources (e.g., [src/cuda/benchmarks/groupby/groupby_nvbench.cu](src/cuda/benchmarks/groupby/groupby_nvbench.cu#L8-L120)), but ROCm build no longer links NVTX. Hipify won’t auto-drop these, causing compile errors unless guarded.
- Cooperative groups API breadth: string kernels use tiled partitions and collective ops (e.g., [src/cuda/string/string_fast.cu](src/cuda/string/string_fast.cu#L1-L140)); HIP CG support is narrower, so some collectives may compile but run differently without auditing wavefront semantics.

## Porting suggestions
- Replace hard-coded warp = 32 logic with `warp_size()`/`cg::coalesced_group` or HIP `warpSize`, and size shared buffers from the runtime warp size; use 64-bit ballot masks on ROCm.
- Introduce arch macros in CMake (`-DROCm_gfx90a` or derive from `CMAKE_HIP_ARCHITECTURES`) to populate `device_info.hpp`; consider replacing the static_assert with runtime queries.
- Audit dynamic shared memory footprints per kernel against 64 KB LDS; gate `hipFuncSetAttribute` with `#if defined(__HIP_PLATFORM_AMD__)` and fall back to smaller tile sizes if needed.
- Add ROCm targets in benchmarks/tests CMake and guard NVTX includes; wire hipbench targets instead of `nvbench::main`.
- For groupby hash, confirm hipco equivalents for thread scope/storage or add HIP-specific constructor parameters.
- For cooperative-groups async copy, add HIP paths (e.g., memcpy + barrier) instead of compiling the body out.
